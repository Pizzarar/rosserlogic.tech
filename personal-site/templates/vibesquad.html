AGENTIC DEVELOPMENT ENVIRONMENT

{{ page.title }}

An app for running a squad of AI coding agents. You bring the ideas; it keeps them sorted, keeps each agent in its own lane, sends work to the right model, and checks the work before it gets to you.

Version 0.3.0 is on the stable channel (released Nov 12, 2026), for Windows: a desktop app and a local web UI, with a phone cockpit you can pair over your LAN or a VPN mesh. The Android app is not part of that release. Read the interactive tour of how it works or the v0.3.0 release.

How it works

  1. 1You + Brainstorm

    You've got ideas. You talk them through with your brainstorming buddy, and anything off-topic gets parked so nothing derails.

  2. 2Lead + Workers

    The buddy hands the plan to the lead, who splits it into separate git worktrees and routes each piece by stakes: top models at high effort for security and core-invariant work, smaller models for mechanical work. When a provider passes 95% of its quota, a counterpart profile on another provider takes over. Reviews go to a different model family, and each review has to say whether a change fixes the cause or only hides the symptom.

  3. 3Back to you

    When something needs your call, your phone pings. You say yes or no.

Under the hood: how the program actually works

The three steps above are the short version. Underneath, VibeSquad is a process runner, a local server and a command-line tool, and its agents pass files to each other instead of chat history. Rules below are tagged: a PROMPT RULE is something agents are told to do; a SERVER CHECK is code that refuses the action.

1. Runtime, adapters and local server

The runner/ process starts the coding CLIs you already have signed in (Claude Code, Gemini / Antigravity, OpenCode and Codex) as child sessions, through one adapter per provider; several are driven over the Agent Client Protocol. The server/ process serves the web UI and an HTTP API on port 4180 by default, and routes messages between agents.

The vs command-line tool, and the same actions as MCP tools, are how an agent logs to the team, messages another agent, makes a worktree or waits on other agents. The server listens on 127.0.0.1 only until you turn on LAN or VPN-mesh access.

2. Squads, lanes and file-based handoffs

A Squad is one project. Its hub Lead, the Overlord, looks after the whole Squad, which is split into lanes such as bugs or usage. A lane has a Buddy you talk to, a Lead, and short-lived Workers that each do one block in their own git worktree.

Agents don't inherit each other's chats. What travels is files: each lane keeps a SPEC.md and a TASKS.json, and a restarted Buddy reads a brief of about 5k tokens instead of a chat of about 150k. A Lead is flagged at 150k tokens of context, compacted in place if idle, and handed to a successor at 250k (hard cap 300k). The successor reads a handoff packet, including a Judgment section that the old Lead writes; messages sent to the old Lead are redirected to it.

3. The seven steps of one unit of work

  1. PROMPT RULE

    Talk to the Buddy. It reads the lane brief and checks what already exists (the workflow index, vs --help) before proposing anything new. Off-topic ideas go to an idea inbox.

  2. PROMPT RULE

    Write the plan. A table of blocks: what each touches and which ones clash. Each block is marked Root cause or Workaround, and a workaround has to name the follow-up that replaces it.

  3. SERVER CHECK

    Start a Lead. Refused unless the caller is that lane's Buddy or the Squad's Overlord, the lane exists in the team registry, the profile is a Lead profile and the lane has no live Lead. Role and handoff labels supplied by the caller are stripped.

  4. PROMPT RULE

    Workers in worktrees. The Lead is told to give each Worker its own git worktree (vs worktree create). Separately, in code, a spawn's stakes tier picks the model and effort, and a provider past 95% of its quota hands over to a counterpart profile on another provider.

  5. PROMPT RULE

    Review. A different agent reviews the diff, normally from another model family, and answers whether the change fixes the cause or hides the symptom. Its first line is PASS or FAIL, three counts and the commit it reviewed. Nothing in code forces which reviewer is used.

  6. PROMPT RULE

    Merge. Before merging, the Lead is told to run vs verdict (added after 0.3.0, so not in the 0.3.0 installer). That command is code: it exits 0 only if the reviewer's own first line is a PASS for the exact commit at the branch tip. But nothing stops a merge that skips it. Each merge also carries a trailer saying what the change needs live to take effect (a rebuild, a reload, a runner or server restart).

  7. PROMPT RULE

    Release. Agents are told never to run release, publish, tag or signing scripts. They send a request to the Release Desk lane, and you give the final go.

4. Per-agent identity, loopback proofs and pairing

SERVER CHECK

When the runner starts an agent it makes a random 32-byte token for it and hands it over only as an environment variable of that agent's process. It stays in memory: never in a command line, a log or a saved file. Every vs or MCP write from an agent carries the token and the server compares it in constant time. A request that names an agent but has a missing or wrong token is refused with a 403 before anything is sent, and is never treated as the owner. A Worker may write only metric entries and its own done or blocker entries to the team log. This was a breaking change in 0.3.0: a script that calls vs with an agent id but no token now gets a 403.

Before any client sends a token, the vs tool, the MCP server and the desktop proxy ask the local server for a signed proof (an HMAC over a fresh nonce and the port) over the same connection, so a different program listening on that port never receives it. Browser writes that rely on a cookie need a same-origin proof.

To pair a phone you scan a QR code or type a one-time 6-digit code, compare the CA fingerprint, and can revoke any paired device at once. The end-to-end-encrypted relay is wired in on the host side but off by default; it only starts if you hand-edit a wss:// endpoint into your settings, and no hosted relay ships. Agents run as your own OS user, so this separates agents' identities from each other, not from your files.

How I got here

  1. "I was getting lost in the sauce."

    Too many agent chats, no idea who was doing what.

  2. "I wanted one place to see the team,"

    so I built my own team-first UI.

  3. "Then it needed structure":

    lanes, a lead per lane, workers under each lead.

  4. "Then lanes grew into Squads":

    one squad per project, each with its brainstorm buddy and lead paired up, and workers underneath.

  5. "Then it needed to feel like chat":

    tabs, split view, focus mode, pasted images.

  6. "Then the talking got its own flow":

    the brainstorm buddy, an idea inbox, restarting a long chat from a short summary.

  7. "Then I wanted it on my phone":

    phone app (PWA) and a desktop app.

  8. "Then it needed to install like a real app":

    a one-step Windows installer with its runtime bundled, a first-run checklist, and signed auto-updates on a stable or beta channel.

  9. "Then it needed to be a full dev environment":

    changes, files, terminal and scripts panels; a command palette (Ctrl+K); search across transcripts; rewind, fork and export a chat.

  10. "Then squads got an overview":

    a card per squad with a monogram emblem, a Needs-you count, the squad's team avatars and its lead's status.

  11. "Then the squad moved into an office tower":

    RiffBot (the squad's brainstorm buddy) and the Overlord (its lead) get a TV each in the sky above the tower. Below, each lane is an office floor with desks, a lead's desk and a shared elevator.

  12. "Then lanes learned to check their own work":

    each lane keeps a SPEC.md and a TASKS.json. Plans label every block "Root cause" or "Workaround", and a reviewer from a different model family has to answer whether a change fixes the cause or hides the symptom. A timeout bump, retry loop or swallowed error fails unless a follow-up replaces it. Each spawn also carries a stakes tier (tierA-security, tierA-invariant, normal or mechanical) that picks the model and effort. Every project gets a Bugs quick-chip for reporting a bug, and merges carry a Live-Needs: trailer that declares what the change needs live to take effect.

  13. "Then it started auditing its own usage, and judging its own workflows":

    a usage panel shows each provider's % left, reset time and burn rate and a split of tokens by role, and later gained a Squad filter. On a schedule (off, or every 6 hours up to every 2 weeks, or on demand) an Opus review and a Gemini review read the numbers and suggest routing changes; the prompt also hands them the previous review's advice to grade against the new numbers. Their suggestions, and bug reports, land in a mail-style triage inbox in a CRT-style Perfection panel at the top, where you accept or reject each one. Below it, a trend view splits clean shipping from rework, loops and restarts. Three additions landed after 0.3.0 and are not in the 0.3.0 installer: a scorecard of how autonomous the squads are (units per owner touch, the streak of merges with no help, needs-you pings per unit, stalls), a gauge comparing the runner's spawn-to-ready time with the old third-party daemon's, and last-10-versus-prior-10 cohort trends. The work is split in three: Usage measures, a Workflows lane judges, and the Bugs lane fixes. Workflows turns a doubt into an A/B routing or boot experiment and logs a keep, change or ruled-out verdict, shipped as config or code rather than another prompt rule. Screens use sample data.

  14. "Then it got a Normal mode alongside Psycho":

    a first-launch layout picker, and a one-click toggle in the toolbar or sidebar, swaps the whole app between Psycho (the pixel-art office tower with sky TVs and animated sprites) and Normal (a plain layout with a project and conversation sidebar, a centered chat, and card-grid dashboards) without losing your place. (On the phone the same toggle is labelled Corpo.)

  15. "Then 0.3 froze features to harden the runner and phone cockpit":

    for 0.3, new features stopped so every lane only chased bugs, security and stability, and 0.3.0 shipped on the stable channel on Nov 12, 2026. VibeSquad's own agent runner replaced the old third-party daemon completely. vs restart waits for active turns, restarts the runner and server, and resumes agents that were cut off mid-turn. Each agent gets its own memory-only token, and cookie writes need a same-origin proof. The phone got a dedicated cockpit with Overlord, RiffBot and Buddy tabs, a quick bug sheet and a one-tap Claude/Gemini switch. Pairing is by QR code or 6-digit code over LAN or a VPN mesh, checked against the host's CA fingerprint, and a paired device can be revoked at once. An end-to-end-encrypted relay (X25519 key agreement, AES-256-GCM) is designed and wired on the host side, off by default, with no hosted relay. The pairing screen here is a mock-up with placeholder values, not a real session.

What it saved

  • MEASURED

    New leads in the VibeSquad lane now start at 3k–4k tokens of context (3 measurements, one lead), down from about 80k after reading a handoff. Escape From Idle leads still start at 87k–155k; trimming its rules is next.

  • MEASURED

    Workers get about 770 characters of team rules (about 200 tokens) instead of the lead-only rules. Before the split, one project's rules file put about 5.5k tokens into every worker start, and 68% of it was lead-only.

  • PROJECTED

    A restarted brainstorm reads a short lane summary (about 5k tokens) instead of carrying a chat of about 150k.

  • MEASURED

    A 41-task checklist of everyday jobs in an agent IDE: 21 passed at v0.1.1, 41 passed after two rounds of work.

  • MEASURED

    Across 426 merged units logged by the usage ledger in its first week (Nov 1-8, 2026), 420 needed one review round or none and 6 needed two or more; 9 (2%) were fixed after merge. One user, one machine, and 394 of the units carry no workflow tag, so this is not a comparison between workflows.

  • MEASURED

    Two runner fixes for desktop disconnects: the worst cold status-scan stall dropped from 4,101 ms to 29 ms (the scan now yields between slices), and runner boot dropped from about 2.25 s to about 1.3 s on a 199 MB agent directory (each log is parsed once). Over the 10 days to the 0.3 freeze (Nov 1–10, 2026) the repo reached 1,898 commits, about 90,000 lines of application code and about 61,700 lines of tests in 316 test files. The full suite at the v0.3.0 build was 3,477 tests in 220 suites: 3,466 passing, 0 failing, 11 skipped. The release covers 242 commits since 0.2.9. After 0.3.0, the Usage panel's ready-time gauge was added; it uses reference figures of about 0.45 s for a runner spawn against about 165 s for the old third-party daemon (about 367 times faster; the gauge states it as a fixed baseline, not a per-run measurement). Raw line counts include blanks and comments, and most commits are agents committing often, so this is throughput, not hand-typed work.
